第一步：先别急着开 IDA

我见过不少人拿到 so 直接扔进 IDA，然后对着三千行反汇编发呆。
先花五分钟搞清楚它的骨架。

stripped。

导出的符号就那几个标准的：JNI_OnLoad？没有。

也没有。
这时候基本可以确定：动态注册，而且 JNI_OnLoad 被隐藏了（或者被 strip 掉了）。

静态：先看骨架，别看细节

函数几百行。
如果你一行行读，三天也读不完。
我的办法是先看调用关系。
getSign 的伪代码大致是：

BL   sub_1E700      ; hex
RET

四五个调用，结构就出来了。
剩下的问题是：这几个 sub 各干什么？

判断算法靠常量表，不靠脑子

这一招我用了很多年，比看汇编快十倍。
MD5 的实现里一定有这四个初值：

0x67452301  0xefcdab89  0x98badcfe  0x10325476

在 Hex View 里搜 little-endian 的字节序列：

01 23 45 67 89 AB CD EF FE DC BA 98 76 54 32 10

搜到就是 MD5。
SHA256 是：

6a09e667 bb67ae85 3c6ef372 a54ff53a

AES 的 S 盒开头：

63 7c 77 7b f2 6b 6f c5 30 01 67 2b fe d7 ab 76

RC4 更好认：找一段 256 字节的循环填充，00 01 02 03 ... FF。
我在这个 so 里同时搜到了 MD5 的 IV 和一个 RC4 的 S 盒初始化痕迹。
基本能确定：MD5 + RC4。
还要一个常量解密（sub_1A2C0），那是 key 的来源。

静态看不动的，交给 frida

静态只能告诉你「调了 MD5」，不能告诉你「MD5 的输入是什么」。
这部分只能动态。
把每个 sub 都 attach 上：

        if (!range) return null;
        if (range.protection.indexOf('r') < 0) return null;

    换路：unidbg

    frida 一直不稳，我转头试了 unidbg。
    思路是：不跟你玩动态对抗了，我直接在 PC 上用 unicorn 模拟执行 ARM 指令，把 JNI 环境模拟出来，直接调 getSign。
    好处是快、可批量、能下断点，而且它不在设备上跑，你的反调试全是废纸。
    坏处是环境得自己补。

    搭骨架

    但 unidbg 只能算，不能解释

    它让你能算，不代表你懂了。
    要真正还原，还是得回到 IDA。
    这时候 unidbg 有个巨大优势：能下断点，能看每个函数的入参出参，不用跟反调试斗智斗勇。

    配合前面 frida 已经确认的算法组合，逐个验证：

    sub_1A2C0 → 异或解密常量，得到 RC4 key
sub_1B550 → RC4 加密明文
sub_1D3F0 → MD5(密文 + 时间戳)
sub_1E700 → 转 hex 大写

    最终结构：

    sign = MD5( RC4(key, 参数串) + 时间戳 ).toUpperCase()
key  = 每次启动时用异或解出来的常量

    Python 复现

    踩过的坑，一条条列

    RegisterNatives 不加过滤等于自杀。 全系统都在调，你要找的那条会淹在几百条里。按 returnAddress 查模块。
    readCString 会崩。 参数可能不是字符串指针。先 findRangeByAddress 查可读性。
    JNI_OnLoad 不一定导出。 被 strip 或者 visibility("hidden") 就找不到，只能靠 hook dlopen/dlsym 追。
    常量搜索比读汇编快十倍。 MD5 IV、SHA256 IV、AES S 盒、RC4 的 0-255 填充，都是可以盲搜的特征。
    unidbg 补环境别贪全。 跑到哪报错补哪，一次补四十个方法纯属自虐。
    frida 和 unidbg 交叉验证。 同一条输入两边算出一样的结果，你才能确定还原对了。
    反调试先解决再分析。 带着反调试硬跑，你永远分不清崩溃是反调试还是自己 hook 错了。这一点我吃了两天的亏。
