参考资料：Anti-Bot 安全 SDK SGAVMP 浅析 ― 吾爱破解论坛
样本版本：libsgmainso-6.4.xxx.so

一、背景与整体思路

在分析无线保镖（SecurityGuard / SGAVMP）生成 ckey的过程中，虽然核心签名逻辑进入了 AVMP 虚拟机（字节码位于图片容器的 bc_sgcipher 段），但绝大多数底层基础密码学原语与数据编解码并未完全虚拟化，而是通过统一的算法分发器（Dispatcher）在 Native 层调用，或通过标准分组哈希结构在 VM 内执行。

只分析加密算法，风控设备注册没有。

整体还原路径分为四个阶段：

  1. 定位算法分发器：通过 IDA + Frida Hook 还原安全图片（yw_1222*.jpg）与本地存储（SG_INNER_DATA）的多层解密流程。
  2. 解析安全图片容器：拆解 yw_1222 伪装 JPEG 头部的二进制结构，提取 KV 密钥表、RSA 公钥、UUID 与内嵌 VM 字节码。
  3. 还原设备指纹组包（dev_data）：还原 60901 / 60902 指令中设备信息的双字节异或、Zlib 压缩与 AES-128-CBC 封装逻辑。
  4. Trace 还原 VM 签名算法（sign）：利用 Unidbg 在外层 SHA-1 完成后开启指令级 Trace，结合 AI 辅助分析识别出 VM 内部实质为标准 HMAC-SHA1。

二、Native 算法分发器（Dispatcher）定位

首先利用ida在sgmain中找到用于加解密算法分发的函数，主要函数有下面几个

function cmdName(cmd) {
    switch (cmd) {
        case 0x03: return 'RC4';
        case 0x10: return 'AES-128-CBC';
        case 0x11: return 'AES-192-CBC';
        case 0x12: return 'AES-256-CBC';
        case 0x14: return 'ZLIB';
        case 0x15: return 'BASE64';
        case 0x16: return 'MD5';
        case 0x17: return 'HMAC-SHA1';
        case 0x18: return 'SHA1';
        case 0x19: return 'SHA256';
        default:   return 'UNKNOWN';
    }
}

三、阶段一：安全图片容器（yw_1222*.jpg）结构与解密

无线保镖将核心配置、动态密钥表以及 VM 字节码隐藏在伪装成 3x3 像素的 JPEG 图片资源中（如硬编码在 SO 中的 yw_1222_0335_mwua，以及 APK 资源目录下的 yw_1222.jpg、yw_1222_mwua_uuid.jpg）。

3.1 容器头部二进制结构（0x000..0x33C，共 828 字节）

字节偏移长度类型字段名含义说明
0x000..0x26C620Bbytesjpeg_cover伪装用的 3x3 标准 JPEG 图像头（FF D8 FF ... FF D9）
0x26C..0x2704Bchar[4]magic固定魔数 "hmqw"（68 6d 71 77）
0x270..0x28016Bbytesheader_digest头部校验摘要
0x288..0x28C4Bu32lerecord1_total_len记录总长度 = 0x33C + payload_len + 4
0x290..0x2944Bu32lepayload_len0x33C 偏移处的主密文长度
0x298..0x2C040Bu32le[10]section_table解压后各子段（KV/RSA、白盒表、JSON、VM 字节码）的长度与 Tag
0x2D8..0x2EC20B16B+4Biv1_slot前 16B 为 iv1（供第 2 层 AES-128-CBC 使用）
0x2EC..0x30020B16B+4Biv0_slot前 16B 为 iv0（供第 1、4 层 AES-192-CBC 使用）
0x300..0x31420B16B+4Biv2_slot前 16B 为 iv2（供第 3 层 AES-256-CBC 使用）
0x314..0x31D9B6B+3Bmycpzu_desc"mycpzu" + 11 13 01（首层解密算法：0x11 = AES-192-CBC）
0x31D..0x32C15B4B+11Bhekg_desc"hekg" + 03 01 +共 3 层解密算法（：12 08 01 [AES-256]、10 15 01 [AES-128]、11 04 01 [AES-192]）
0x32C..0x33C16B6B+10Bdspvor_desc"dspvor" 尾部标记块

3.2 四层 AES 嵌套解密与 Zlib 解压

读取 0x33C 处的密文后，按头部调度块指示的顺序执行 4 次 AES-CBC 解密（密钥硬编码于 libsgmainso.so 以及CERT.RSA里面，IV 取自头部对应的 iv0/iv1/iv2 槽位）：

  1. 第 1 层：AES-192-CBC（cmd = 0x11，使用 iv0）
  2. 第 2 层：AES-128-CBC（cmd = 0x10，使用 iv1，取自 hekg_desc 逆序第 1 项）
  3. 第 3 层：AES-256-CBC（cmd = 0x12，使用 iv2，取自 hekg_desc 逆序第 2 项）
  4. 第 4 层：AES-192-CBC（cmd = 0x11，使用 iv0，取自 hekg_desc 逆序第 3 项）
  5. 解压还原：对第 4 层去填充后的明文执行 Zlib 解压，得到 sg_dynamic_data 格式的动态数据。

四、阶段二：本地存储 SG_INNER_DATA 双层解密提取 eeid

在组装设备指纹前，SDK 会读取本地文件 SG_INNER_DATA 中的 SGSAFETOKEN_IN 字段（格式为 "8560&eRuoS..."），通过两层 AES-128-CBC 解密还原出核心设备标识 eeid：

  1. 派生第一层密钥 key1（基于 nc）：

    key1 = IV1 = MD5(nc).hexdigest()[:16]

    用 key1 对 SGSAFETOKEN_IN 中 & 之后的内容进行 Base64 解码与 AES-128-CBC 解密，得到外层 JSON：

    {
 "configlistjson0": "008&/***",
 "6c709c11d2d46a7b": "008&***",
 "8dd236e3120fdbea": "008&/********..."
}

  2. 派生第二层应用绑定密钥 key2（基于 RSA 公钥与包名信息）：
    将图片中提取的 rsa_pubkey_der（原始字节）与包名、机型、版本号拼接：

    buf = rsa_pubkey_der + b"&com.xxx.app&DEVICE_MODEL&VER_CODE&\x00"
key2 = IV2 = MD5(buf).hexdigest()[:16]

  3. 解密获取 eeid：
    取出外层 JSON 中 "8dd236e3120fdbea" 对应的值，去掉 "008&/" 等前导字符（跳过 & 后前 8 个字符），Base64 解码后用 key2 进行 AES-128-CBC 解密，再经 Base64 解码即得到 66 字节的 eeid。

五、阶段三：设备信息组包与加密（生成 dev_data）

调用 doCommandNative(60902) 传入待签名的业务参数（如 ccode=0101****&client_ip=...&client_ts=...&utid=...&vid=...）时，先构造加密的设备信息串 dev_data：

  1. 拼接明文载荷 plain_body：

    • 随机生成 2 字节异或密钥：xor_key = os.urandom(2)（或固定双字节）

    • 拼接固定元数据头、eeid66、状态位及以 \x00 分隔的设备信息字段：

      plain_body = xor_key (2B) + BODY_META + eeid66 (66B) + state + device_info_fields

  2. 双字节交替异或混淆（wua_xor）：
    保持 plain_body 前 5 个字节不变，从第 5 个字节（索引 5）开始，与前 2 字节的 xor_key 交替异或：

    • 相对偏移为偶数位：plain_body[i] ^= plain_body[0]
    • 相对偏移为奇数位：plain_body[i] ^= plain_body[1]

  3. Zlib 压缩与添加魔数头：
    对异或后的数据进行 zlib.compress（level 6），并在头部加上 4 字节固定前缀 \x00\x00\x00\x02：

    aes_in = b"\x00\x00\x00\x02" + zlib.compress(wua_xor(plain_body))

  4. AES-128-CBC 加密与 Base64 编码：
    根据当前所用的 wua_key_index（如 hzI1 / PrCm / wRMV）获取对应的 wua_uuid，计算：

    key3 = IV3 = MD5(wua_uuid).hexdigest()[:16]

    对 aes_in 进行 AES-128-CBC（PKCS#7 填充）加密后进行 Base64 编码，并拼上 wua_key_index 前缀：

    dev_data = f"{wua_key_index}_{base64.b64encode(ciphertext).decode()}"

六、阶段四：外层 SHA-1 与 VM 内部 HMAC-SHA1 签名还原

6.1 外层 SHA-1 预摘要

将业务请求串 input、上一步生成的 dev_data 以及固定尾部标识 tail（如 PZM9_a0010 / YHcu_a0010 / 6vSu_a0010）用 & 拼接，先在 Native 层计算一次标准 SHA-1：

sign_input = f"{input}&{dev_data}&{tail}"
sha1_bytes = hashlib.sha1(sign_input.encode()).digest()  # 20 字节原始摘要

后面的加密就全在vm里面了，能力有限，下面全靠ai分析，只用了三分钟就识别出了vm里面的hmac算法，下面是分析过程。

6.2 Unidbg Trace 结合 AI 识别 VM 内部算法

为了避免全量 Trace 导致日志过大，先通过 Unidbg Hook libsgmainso.so 中的外层 SHA-1 函数，待外层 SHA-1 执行完毕后再开启指令 Trace（生成约 600MB Trace 日志），交由 AI 进行数据流与指令特征分析，仅用两步即确认为标准 HMAC-SHA1：

第一步：从指令特征识别出 SHA-1

  1. 输出长度与末尾累加特征：最终输出为 40 个十六进制字符（160 bit，即 5 个 32 位字）。在 Trace 中反查最终结果的生成指令：

    add r0, r2   r0=0xe69c60d7  r2=0xf107666e  =>  r0=0xd7a3c745

    5 个字均由“两个 32 位值相加”产生，符合 MerkleCDamgård 哈希结构末尾 H[i] += a/b/c/d/e 的典型特征。

  2. 标准魔数与初始向量（IV）：

    • Trace 中出现轮常量 0x5a827999、0x8f1bbcdc、0xca62c1d6（SHA-1 独有轮常量）。
    • 压缩块结束时出现 + 0x67452301、+ 0xefcdab89、+ 0x98badcfe、+ 0x10325476、+ 0xc3d2e1f0（第 5 个常数 0xc3d2e1f0 是区分 SHA-1 与 MD5 的标志）。
第二步：从 4 次压缩块的串联关系识别出 HMAC

梳理 Trace 中全部 4 次 SHA-1 压缩块的输入与状态传递关系：

压缩块初始状态 (IV)消息块 W[0..15] 内容作用说明
①标准 SHA-1 IV64 字节块（后半段全为 0x36363636）内层哈希前缀：K XOR ipad（\x36）
②块 ① 的输出状态外层 SHA-1 的 20 字节结果 + 0x26（"&"）+ 0x80 填充，总位长 0x2a8 bit（85 字节 = 64 + 21）内层哈希消息：SHA1((K XOR ipad) (sha1_bytes  "&"))
③重置为标准 SHA-1 IV6b6a6c68... + 后半段全为 0x5c5c5c5c外层哈希前缀：K XOR opad
④块 ③ 的输出状态块 ② 输出的 20 字节摘要 + 0x80 填充，总位长 0x2a0 bit（84 字节 = 64 + 20）外层哈希汇总：SHA1((K XOR opad)  InnerHash)

核心判定依据与密钥提取：

  • 块 ③ 后半段填充全为 0x5c5c5c5c（因为 Key 长度不足 64 字节，补 0x00 后异或 0x5c 仍为 0x5c）。

  • 直接将块 ③ 前半段字节与 0x5c 异或，即可无损还原出 VM 内部隐藏的 HMAC 密钥：

    6b 6a 6c 68 ... ^ 0x5c  -->  37 36 30 34 ... ("7604****-****-4f91-****-********449c")

  • 块 ② 的消息共有 21 字节，即外层 SHA-1 的 20 字节原始二进制摘要 后面拼接了 1 个字节 0x26（ASCII 字符 "&"）。

提示：Trace 识别 HMAC 的通用经验

  1. 内存中出现连续的 0x36363636（ipad）或 0x5c5c5c5c（opad）。
  2. 标准哈希 IV 在单次调用周期内初始化了两次。
  3. 末尾 bit 长度字段比实际消息多出 64 字节（512 bit，对应 MD5 / SHA-1 / SHA-256 的分组长度）。
  4. 第二轮哈希的输入恰好等于第一轮哈希的摘要输出。

6.3 最终签名与 ckey 拼接公式

# 1. 外层 SHA-1（取 20 字节二进制 digest，并在末尾拼接字节 b"&" 即 0x26）
sign_data = f"{input_params}&{dev_data}&{tail}".encode("utf-8")
msg_21b = hashlib.sha1(sign_data).digest() + b"&"

# 2. VM 内部实质为标准 HMAC-SHA1
final_sign = hmac.new(hmac_key.encode("utf-8"), msg_21b, hashlib.sha1).hexdigest()

# 3. 组合成最终的 ckey
ckey = f"{dev_data}&{tail}{final_sign}"
