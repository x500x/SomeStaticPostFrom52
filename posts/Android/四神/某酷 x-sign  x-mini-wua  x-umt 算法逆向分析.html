某酷 x-sign / x-mini-wua / x-umt 算法逆向分析

阅读本文前，建议先看上一篇关于某酷 CKEY 的逆向分析

基础环境和前置套路跟上一篇一脉相承，重复的部分就不多讲了。核心思路还是一样：在 libsgmainso 里定位到底层加解密算法的统一分发函数（DISPATCH），把 AES、MD5、HMAC-SHA1、Zlib、Base64、RC4 这些基础出入口全部 Hook 住。只要把入参和返回值一打，90% 以上的逻辑顺着日志就能直接盘出来。

下面按从易到难的顺序，分别聊聊 x-umt、x-mini-wua 和 x-sign 这三个头的生成逻辑。

一、x-umt：直接从本地 SGSAFETOKEN_IN 剥离

x-umt 是三个参数里最简单的一个，本质上就是一个持久化的 32 位设备 Token，藏在本地的 SG_INNER_DATA（里的 SGSAFETOKEN_IN 字段）中。

如果你看过上一篇 CKEY 里提取 eeid 的过程，那这一步就非常眼熟了――它的解密算法和 eeid（对应字段 8dd236e3120fdbea）一模一样：

  1. 第一层（外层 JSON 解密）：
    拿内置容器里读出来的 nc（"b2d4r22f9IbzTv9m"）算一次 MD5，取前 16 位小写 Hex（86e101cb117e3c55）同时作为 AES-128-CBC 的 key 和 iv，把 SGSAFETOKEN_IN 解开，得到一个内层 JSON。
  2. 第二层（提取 0357995e9858d8b0）：
    在内层 JSON 里找到 key 为 "0357995e9858d8b0" 的项，长这样： 
    "0357995e9858d8b0": "008&d833c771mv6****"
  3. 解出 x-umt：
    按 & 切开后去掉前面 8 个字符的校验头（d833c771），剩下的 Base64 密文用应用绑定密钥 app_key（即 141B RSA 公钥 + "&包名&机型&code&\x00" 共 178 字节的 MD5 前 16 位，本例中为 `）再跑一次 AES-128-CBC 解密（key = iv = app_key），解出来的 32 字节明文字符串（例如89Y**`）直接就是请求头里的 x-umt**。

二、x-mini-wua（HHnB_）：精简版 CKEY

抓包看到的 x-mini-wua 形如 HHnB_eXfjRCeGQxuyHrJ2...（对应 doCommandNative 的 cmd=20102）。

拿它的 Frida 日志跟之前 CKEY 的 wRMV_ 对比一下就会发现：它其实就是把 CKEY 尾巴上的 &6vSu_... 签名段砍掉了，并且把里面的设备信息组包换成了更紧凑的 82 字节定长结构，其余加密套路完全一致。

具体组包和加密步骤如下：

  1. 拼接 82 字节明文体 plain_body： 
    plain_body = (
   xor_key                      # 2B 随机异或密钥，例如 b"\xca\x90"
   + b"\x42\x24\x02"            # 3B 固定头部标识 (BODY_META_3B)
   + eeid66                     # 66B 原始二进制 eeid (从 8dd236e3120fdbea 解出后再 Base64 解码)
   + bytes.fromhex("800000223300")  # ??? 6B 环境检测状态位 (state6)
   + struct.pack(">I", timestamp)   # 4B 大端秒级时间戳
   + b"\x00"                    # 1B 结尾 0x00
)
  2. 双字节交替异或混淆：
    跟 CKEY 一样，保留 plain_body 前 5 个字节不动，从第 5 字节（即 eeid66 开头）起，依次与 xor_key[0]、xor_key[1] 循环异或。
  3. 加 4B 帧头并做 AES-128-CBC 加密：
    • 在异或后的 82 字节前面加上 4 字节固定帧头 b"\x00\x00\x00\x03"，凑成 86 字节。
    • 从内置容器 KV 表里取出 wua_key_index（"HHnB"）对应的 UUID（"f19b7bc7-..."），求 MD5 后取前 16 位小写 Hex 作为 AES-128-CBC 的 key 和 iv。
    • 对 86 字节数据做 PKCS#7 填充（96 字节）并加密，最后转成 Base64，拼上 "HHnB_" 前缀即可。

三、x-sign（cmd=10401）：白盒 AES 还原与双层 HMAC-SHA1

x-sign（对应 doCommandNative 的 cmd=10401，返回值形如 ab2c03009030464876...）看着最唬人，用到了安全保镖的白盒 AES。

但正所谓“重剑无锋”，之前我们就提到过一个重要经验：安全保镖真正塞进 AVMP 虚拟机里纯软实现的算法其实非常少，VM 更多只是充当一个调度壳（胶水层），核心的密码学原语依然要走底层的算法分发器或标准查表。多抓几个样本对比一下输入输出，甚至都不需要去硬啃 VM 字节码，就能把整个链路摸清楚。

第一步：拆解两处加密图片容器，拿到关键材料

在初始化阶段，libsgmainso 会先后用四层链式 AES-CBC（AES-192 -> AES-128 -> AES-256 -> AES-192）加 Zlib 解压两份 hmqw 格式的容器数据：

  1. 先解 SO 内置的 4000B 容器（文件偏移 0xd94bc）：
    从它的 KV 表里可以拿到两个全局关键常量：
    • 白盒初始向量 white_iv：b"6zi8********cUh1"（16B）
    • 白盒轮次控制块解密密钥 innerk1：b"AsWj********21Yv"（16B）
  2. 再解 APK 资源目录里的 res/drawable/yw_1222.jpg：
    解压出 308,948 字节的明文动态数据，里面主要包含两部分核心数据：
    • 业务 KV 表（5,188 字节）：存放当前包名（com.xxx.xxx.tv）下的各类密钥，其中就包括当前 <APP_KEY> 对应的 32 字节签名密钥 secret（"2ce28f6c********************6b3f"）。
    • 白盒 AES 查找表段（303,702 字节）：包含 a6666 和 b2c03 两组白盒表，每组正好都是 151,808 字节。

拿到这两组白盒表后，直接把二进制结构喂给 AI 做代数特征分析，十分钟不到就把底层的 16 字节原始 AES-128 密钥给扒出来了。下面是ai分析的这套白盒表是怎么排布的，以及为什么能直接还原出明文 Key。

第二步：白盒 AES-128 查找表结构与密钥还原原理

1. 151,808（0x25100）字节白盒表里装了什么？

把 151,808 这个长度拆开看，结构非常工整：

9 × 16384 + 4336 + 16 = 147456 + 4336 + 16 = 151808 字节（0x25100）

它由 9 个 16,384 字节的标准轮 T-Box 块、1 个 4,336 字节的末轮 S-Box 块，外加 1 个 16 字节的尾部加密控制块拼成。

这里面藏了两个小机关：

(1) 尾部 16B 控制块与「轮次乱序（Round Shuffling）」

如果你直接按顺序把第 0 块当成 AES 第 0 轮去算，肯定算不对。玄机就在表尾最后 16 字节（0x250F0..0x25100）的密文 04c8058f********3e498ba8 里。
在初始化日志中可以看到，libsgmainso 用前面内置容器里的 innerk1 对这 16 字节做了一次 AES-128-ECB 解密，去填充后得到 10 个字节：
perm = [7, 0, 4, 5, 6, 9, 8, 1, 2, 3]
这 10 个数字就是物理槽位 Slot 0..9 对应的真实 AES 轮号！因为 perm[5] = 9，所以夹在中间第 5 号槽位（偏移 0x14000..0x150F0）的那块 4,336 字节数据，正好就是 AES-128 的末轮（第 9 轮）表，而真正的首轮（第 0 轮）其实放在第 1 号槽位（偏移 0x4000）。

(2) 前 9 轮（Round 0..8）T-Box 块布局（每块 16 × 1024 = 16,384 字节）
  • 每一轮有 16 张子表（i = 0..15），每张子表是 256 × 4B = 1024 字节。
  • 子表按行优先排列：i = 0..3 对应第 0 行（用标准 TE0），i = 4..7 对应第 1 行（用 TE1），i = 8..11 对应第 2 行（用 TE2），i = 12..15 对应第 3 行（用 TE3）。
  • 因为 AES 的 ShiftRows 被提前合并进了查表索引，第 i 张子表读取的输入字节下标为 state[SR_IDX[i]]：
    SR_IDX = [0, 4, 8, 12, 5, 9, 13, 1, 10, 14, 2, 6, 15, 3, 7, 11]
(3) 末轮（Round 9）块布局（0x14000..0x150F0，共 16 × 271 = 4,336 字节）
  • 末轮不做 MixColumns，每张子表 i = 0..15 占 271 字节（16 + 255 字节）：
    • 当输入 x = 0 时：存为前 16 字节稀疏向量 rec[0:16]，其中只有第 i 个字节通道 rec[i] 是有效输出，其余 15 个字节全是 0x00。
    • 当输入 x = 1..255 时：干脆省掉了那 15 个零字节，直接紧缩存为后 255 个单字节 rec[16:271]（即 x ≥ 1 时的输出值为 rec[15 + x]）。
  • 末轮输出写回 out[TR_IDX[i]]，其中 TR_IDX 是标准 4 × 4 行列转置下标：
    TR_IDX = [0, 4, 8, 12, 1, 5, 9, 13, 2, 6, 10, 14, 3, 7, 11, 15]
2. 为什么这组白盒表能被轻松还原？（5 条代数原理验证）

这组白盒实际上是一个既没有外部输入/输出编码、内部线性混淆矩阵也退化为单位阵 I 的简化版白盒（主要靠轮次打乱和末轮变长结构来做工程混淆）：

编号核心代数原理本样本实测表现还原中的实际作用
原理 1表是「字节函数 × 线性映射 + 常量」满足（144 张表 GF(2) 秩恒为 8）对前 9 轮全部 144 张表的输出做线性无关检测，秩全部恒为 8。不仅说明没有引入非线性 4-bit 扰动，而且实测其线性映射矩阵直接就是标准 TE 表本身（M_i = I_32，c = 0）。
原理 2末轮无输出编码满足（末轮表仅 1 个变化通道）末轮 rec[0:16] 中只有通道 i 非零，输出直接就是 y_i(x) = SBOX(x rk9[SR(i)]) rk10[TR(i)]。末轮轮密钥 rk10 作为“值常量”裸露在表输出端。
原理 3末轮 SubBytes 后异或轮密钥满足（InvSbox(y(x) c) 为仿射）枚举值常量候选 c = 0..255，计算 g_c(x) = InvSbox(y_i(x) c)。只有当 c 猜中真实的 rk10[TR(i)] 时，外层 S-Box 才会被完美抵消，使得 g_c(x) x 退化为常数 rk9[SR(i)]。一步就能同时把 rk10 和 rk9 两个轮密钥解出来。
原理 4首轮以原始输入为索引、AddRoundKey 在 SubBytes 前满足（前 9 轮均无输入编码）前 9 轮的子表满足 T_i^(r)(x) = TE(i // 4)(x rk[r][SR(i)])。直接在表里搜哪个下标 x 的值等于 TE(i // 4)(0)，那个下标 x 就是轮密钥字节 rk[r][SR(i)]（“索引常量”直接暴露）。
原理 5密钥编排可交叉验证满足（双路径 100% 互证，可盲推轮序）路径 A 从首轮（0x4000）提索引常量直接拿 rk0；路径 B 从末轮（0x14000）用仿射判别拿 rk10 再逆推回 rk0。两条路算出来的 11 轮密钥分毫不差；甚至哪怕没有 innerk1，靠逆密钥编排也能直接盲推出 [7, 0, 4, 5, 6, 9, 8, 1, 2, 3] 的轮次顺序。

第三步：x-sign（cmd=10401）五步签名流水线还原

把白盒变成了标准 AES-128-CBC 之后，再回来看 cmd=10401 的 Frida 调用日志，整个算法就彻底透明了：

整个生成过程就是非常干脆的 HMAC-SHA1 -> 白盒 AES-128-CBC -> Base64 -> HMAC-SHA1 五步流水线：

  1. 准备密钥：
    • 根据 appKey 从 yw_1222.jpg 的 KV 表查出 32 字节 secret = "2ce28f6c********************6b3f"。
    • 根据 authCode = "uuid" 选用 b2c03 白盒表（对应刚刚还原出的 16B 明文密钥 wb_key = b"DSRp********N06W"），搭配内置容器的 white_iv = b"6zi8********cUh1"。
  2. 第一次 HMAC-SHA1（生成 h1）：
    用 secret 作为密钥，对传入的 INPUT 串算一次 HMAC-SHA1，转为 40 位小写 Hex 字符串 h1（cce8944d************************30457456）。
  3. 构造 73B 明文并做白盒 AES-128-CBC 加密：
    把 40 位的 h1 和 32 位的 secret 用 "&" 拼起来，得到 73 字节明文：
    wb_pt = h1 + "&" + secret（40 + 1 + 32 = 73B）
    做标准 PKCS#7 填充（补 7 个 0x07 到 80 字节），然后用 key = wb_key、iv = white_iv 跑一遍标准 AES-128-CBC 加密，拿到 80 字节密文。
  4. 标准 Base64 编码：
    把 80 字节密文编码成 108 字节的 Base64 字符串（bWe3GmTfJUm7vEjK...ji2DSKk=）。
  5. 第二次 HMAC-SHA1 与前缀拼装：
    用同一个 secret 对这 108 字节 Base64 字符串再算一次 HMAC-SHA1，得到 40 位小写 Hex 摘要 h2（30464876************************37ab7216）。最后拼上固定前缀 "a" + 白盒表名 ("b2c03") + "0090"，就是最终 50 位的 x-sign：
    x-sign = "ab2c030090" + h2

四、核心 Python 还原代码（脱敏版）

import base64
import hashlib
import hmac
import struct

# 1. 核心密钥材料（由容器解密与白盒代数还原获得，此处已脱敏）
APP_SECRET = "2ce28f6c********************6b3f"  # 32B，来自 yw_1222.jpg KV 表
WB_NAME    = "b2c03"                             # 白盒表名
WB_AES_KEY = b"DSRp********N06W"                 # 16B，由 b2c03 还原出的 AES-128 明文密钥
WHITE_IV   = b"6zi8********cUh1"                 # 16B，来自 SO 内置容器 KV 表 white_iv
WUA_UUID   = "f19b7bc7-****-****-****-8892a50fdf51"

def gen_x_mini_wua(eeid66: bytes, xor_key: bytes, timestamp: int, aes_cbc_enc_fn) -> str:
    """生成 x-mini-wua (HHnB_...)"""
    plain_body = (
        xor_key
        + b"\x42\x24\x02"
        + eeid66
        + bytes.fromhex("800000223300")
        + struct.pack(">I", timestamp)
        + b"\x00"
    )
    # 从偏移 5 开始双字节交替异或
    obf = bytearray(plain_body)
    for i in range(5, len(obf)):
        obf[i] ^= xor_key[(i - 5) & 1]

    aes_in = b"\x00\x00\x00\x03" + bytes(obf)
    key = hashlib.md5(WUA_UUID.encode()).hexdigest()[:16].encode()
    ct = aes_cbc_enc_fn(key=key, iv=key, plaintext=aes_in)
    return "HHnB_" + base64.b64encode(ct).decode("ascii")

def gen_x_sign(input_str: str, aes_cbc_enc_fn) -> str:
    """生成 x-sign (ab2c030090...)"""
    secret_bytes = APP_SECRET.encode("utf-8")

    # Step 1: 第一次 HMAC-SHA1
    h1_hex = hmac.new(secret_bytes, input_str.encode("utf-8"), hashlib.sha1).hexdigest()

    # Step 2: 拼接 "{h1_hex}&{APP_SECRET}" (73B) -> PKCS#7 填充 (80B) -> 白盒等价 AES-128-CBC
    wb_pt = f"{h1_hex}&{APP_SECRET}".encode("utf-8")
    ct_80b = aes_cbc_enc_fn(key=WB_AES_KEY, iv=WHITE_IV, plaintext=wb_pt)

    # Step 3: Base64 编码 (80B -> 108B)
    b64_bytes = base64.b64encode(ct_80b)

    # Step 4: 第二次 HMAC-SHA1
    h2_hex = hmac.new(secret_bytes, b64_bytes, hashlib.sha1).hexdigest()

    # Step 5: 拼接前缀返回
    return f"a{WB_NAME}0090{h2_hex}"
