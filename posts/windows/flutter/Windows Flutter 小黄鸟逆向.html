逆向里 AI 已经能扛很重的活：搜串、xref、解函数、画图。人更适合干三件事――定目标、喂线索、纠偏。

别一上来就丢「帮我破解」。更稳的问法是：先逼它交出一张「共享核心」总图，确认 AES 和 镜像管理规则 打的是同一套本地 vip，再谈改哪一刀。

本文以 Windows 端小黄鸟（Flutter / app.so）为例，记录这条顺序是怎么走通的。

一、突破口先放出来

第一句其实很朴素：

帮我梳理整个校验流程：从 AES 功能使用，到镜像里的管理规则 / 免费额度限制。
先画调用链，标出两边是否汇合；先别给补丁。

它追完字符串和 xref 之后，大致会交出下面这张图――这就是整篇的突破口：

图1 突破口：AES / 镜像管理规则都汇入同一套「共享权益」判断

我会这样验收这张图，方向才算定住：层次路径
共享核心取账号 → vip → isPremium → lifetime / expireTime
镜像门禁vip == null → 401；非 premium → 403；通过才真正创建 / 改 / 删
AES 门禁vip == null → 登录引导；非 premium → 升级弹窗；通过才打开工具
结论两处都打「共享核心」，不要只改某一个 UI 入口

后面所有步骤，其实只回答两件事：

  1. 这张图我是怎么问出来的；
  2. 共享核心里，改哪一刀最划算。

总图不是空想，是对着真实现象追的。先把破解标识钉死，再丢给 AI。

图4 「免费额度 0/3」――后面证明 ≠ 镜像真实门槛

三、没有符号 AI 进不去：先把 Blutter 门打开

另一件基建是人来拍板的：得让 AI 读得动 app.so。

Windows Flutter 工具少，就改 Blutter 去吃这份 so（可参考吾爱上「让 Blutter 支持 Windows Flutter」相关帖），跑通后再开 IDA MCP。

图5 Blutter 出符号：后面 xref 的粮草

四、倒叙：这张总图是怎么「问」出来的

突破口是图1，但读者会问：第一步到底跟 AI 说了什么？

顺序很简单――先确定目标，再把目标喂给 AI，让它自己推导验证链；不要一步丢「帮我破解」。

具体就是把第二节的三张现象图 + 第一节那句梳理要求一起丢过去，逼它从 AES 追到镜像，并标出两边是否汇合：


图6 把目标喂给 AI 后：它推出 AES / 镜像汇入共享权益的验证链

总图出来以后，再观察哪里适合作为攻击点――后面确认就是共享核心里的 vip。

五、共享核心里，对象到底长什么样

总图里已经出现 Lab.vip。下一步不要自己猜布局，直接问：

共享核心里的 Account / 账号体结构应该是怎样的？

AI 归纳出来的结构可以收成这样：

图：Account → 账号体 +0x2F（vip）→ expireTime / lifetime

验收点：

  • 门禁读的是账号体 +0x2F 上的 vip
  • 不是账号体自己的 +0x07 字段
  • Account+0x07 是整层指针；体内 +0x07 是另一层――别混

六、突破口之后：改门禁，还是改 vip「出生点」？

有了图1，AI 很容易建议 hook isPremium，或直接改 AES 返回值。这时要把问题扳到更划算的位置：

共享核心确认了。下一步别先改门禁。
问：vip 是什么时候造出来的？请从 JSON 字段 / 解析链定位，不要先假设函数名。

6.1 让 AI 自己把解析链画出来

顺着上面那问，AI 会把这条链摊开：

账号 JSON
  → 取 vip 子 Map
  → 解析成小对象
  → 写回账号体 +0x2F

理想写死点就在「vip 子对象被 Allocate 出来、填 expireTime / lifetime」这一层――对象仍由 Dart 自己分配，不用手搓堆。

图7 AI 给出的解析链：vip 子对象解析 → 写回账号体 +0x2F（出生点）

继续追具体偏移：

在获取 JSON 的那一刻，具体在哪个偏移？你知道吗

常见情况是：账号拉取和许可证 / 绑卡更新都会走到同一处――所以改「vip 出生点」通常比只改 AES 门禁划算。整层伪造账号体也能做，但字段多、易崩。

最终目标：瞄准 JSON Map 里 vip 的解析位置。

七、纠偏：免费号 vip=null，成功尾声补丁会空跑

以为准备收工时一跑，发现还是没效果：

问题很清楚：网络下来就是 vip == null，解析入口直接 return，根本走不到改过的「成功路径」。

接下来就简单了――要在函数开头、还没进 vip:null 早退之前就替换：

图：入口直接 Allocate 合法 vip（lifetime=true / 远未来），再写回 Lab+0x2F

八、结果

共享核心方向对了，验证就简单：镜像列表可以正常新建多条规则。


图8 验证：管理规则可创建（突破口打在共享权益上）

九、当时的提问顺序（给想复现的人）

不是标准答案，只是对照正文里真实走过的问法：

  1. 帮我梳理整个校验流程：从 AES 到镜像管理规则 / 免费额度
    （先出总图、标两边是否汇合，先别补丁）
  2. 额度文案和真实门禁是不是一回事？
  3. 共享核心里的 Account / 账号体结构应该是怎样的？
  4. vip 是什么时候造出来的？
    请从 JSON 字段 / 解析链定位，不要先假设函数名
  5. 谁调用了？写回账号体哪个偏移？
    获取 JSON 的那一刻，具体在哪个偏移？
  6. 要在函数开头、还没进 vip:null 的时候就替换掉
  7. 我触发登录 / 点 AES / 建镜像做验收；AI 解释与改点

顺序的关键是：

共享核心总图 → 对象布局 → 出生点偏移 → 最后才处理 null 早退

反过来，很容易在单个弹窗或成功尾声补丁上打转。

十、收束

突破口就是图1 那句：共享核心，两处都打这里。

  • 人负责：把 AI 问到交出这张图，并在 null 路径、额度文案、改点选择上纠偏
  • AI 负责：把 Flutter / app.so 里的脏活干完

先有共享权益总图，再谈伪造 vip 对象――顺序反了，就容易在单个弹窗上打转。
