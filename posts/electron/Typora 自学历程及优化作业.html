二、各方案差异及优缺点

通过对上述帖子的研究，Typora破解主要存在以下几种技术路线：

方案一：Hook注入方案（本方案采用）

原理：在 launch.dist.js 中注入Hook代码，拦截关键函数调用（crypto.publicDecrypt、网络请求、注册表操作等），伪造验证结果。

优点：

  • 实现相对简单，不需要深入逆向JSC字节码
  • 兼容性较好，适用于多个版本
  • 可动态调整，灵活性强

缺点：

  • 依赖 launch.dist.js 入口文件，若该文件被大幅修改则需要适配
  • 需要修改Fuse配置让程序从解包目录加载

方案二：公钥替换方案

原理：将Typora内置的RSA公钥替换为自己生成的公钥，然后用对应的私钥签发License。

优点：

  • 一劳永逸，可自己生成任意License
  • 技术层面更彻底

缺点：

  • 需要逆向JSC字节码找到公钥位置，技术门槛高
  • 不同版本公钥位置可能变化，维护成本高

方案三：注册表重置方案

原理：定时重置注册表中的试用期信息，实现无限试用。

优点：

  • 实现最简单，不修改程序文件
  • 风险最低

缺点：

  • 治标不治本，试用期弹窗依然存在
  • 可能被后续版本修复
  • 需要常驻后台进程

方案对比总结

维度Hook注入公钥替换注册表重置
技术门槛中等高低
破解彻底性高最高低
版本兼容性较好较差较好
维护成本中等高低

三、最终方案及借鉴思路

本方案采用 Hook注入 + 多层拦截 的综合策略，借鉴了各帖子的核心思想：

借鉴思路

  1. 反反调试（来自 Thread-2084047） ：通过 flipFuses 修改 Typora.exe 的Fuse配置，将 OnlyLoadAppFromAsar 设为 false，允许程序从解包的 app 目录加载文件。

  2. 完整性校验绕过（来自 Thread-2084047） ：通过 Hook fs 模块的 readFile、stat 等方法，将对 resources/app/ 的访问重定向到 resources/app.bak/，让程序读取原始文件而非修改后的文件。

  3. RSA验证劫持（来自 Thread-2118831） ：Hook crypto.publicDecrypt 方法，直接返回伪造的License对象，包含动态提取的 deviceId 和 fingerprint。

  4. 网络请求拦截（来自 Thread-2084683） ：劫持 dns.lookup、electron.net.fetch、electron.net.request 和 protocol.handle，拦截所有指向 typora.io、typoraio.cn、dian.typora.com.cn 的请求。

  5. 注册表防护（来自 Thread-2084683） ：轮询恢复 SLicense 注册表值，并劫持 child_process.execSync 阻止程序修改注册表。

四、关键修改点及设计理由

4.1 完整性校验绕过

  • JS v1/v2 方式：将 resources/app/ 的文件读取重定向到 resources/app.bak/，保留原始未修改文件。
  • 独立替换文件方式：内存中缓存 launch.dist.bak.js，拦截 fs.readFileSync 等返回备份内容。
  • 最终版选择：采用内存缓存+修补 fs 模块（包括 original-fs），避免依赖外部目录重定向，更干净且不易被检测。
  • 理由：Typora 可能在校验时仅读取 launch.dist.js 而非整个 app/，因此内存缓存更直接；同时 patch original-fs 增强了兼容性。

4.2 RSA publicDecrypt 多层处理

  • JS v2：仅 fallback，原方法优先，失败后返回伪造。
  • 攻击者公钥版：引入 fn_0212 密文头检测 → 攻击者公钥解密 → fallback。
  • 最终版：完全采用攻击者公钥版的顺序，但去除了无效冗余，并保留填充至 256 字节以模拟真实 RSA 块。
  • 理由：fn_0212 是 Typora 内部完整性校验，必须优先绕过；攻击者公钥可能用于验证签名，优先尝试可增加真实感；最终 fallback 保证万无一失。

4.3 注册表写入

  • 外部脚本：由激活脚本一次性写入，但 Hook 内部无防护。
  • 最终版：Hook 启动时立即写入，确保授权数据存在。
  • 理由：若用户仅替换文件而未运行外部脚本，则 Typora 无法识别授权；内置写入实现“开箱即用”。

4.4 网络拦截

  • 攻击者公钥版：使用 webRequest 全域拦截 typora.io，取消所有请求，副作用大。
  • JS v2/最终版：使用 protocol.handle 仅拦截激活和更新 API，其余正常转发。
  • 理由：保持正常联网功能（如主题下载、帮助文档）不影响用户体验，同时防止破解被检测。

4.5 Buffer.equals 绕过

  • 来源：无私钥.js 系列，检测到与 FN0212_EXPECTED 相等的 Buffer 时直接返回 true。
  • 最终版：额外增加密文头检测，不仅匹配哈希，还匹配 16 字节特征头，更准确。
  • 理由：Typora 可能通过 Buffer.equals 比对解密后的哈希，此 Hook 强制放行，是绕过二次校验的关键。

4.6 去除冗余功能

  • 攻击者公钥版 包含大量未实际改变行为的占位 Hook（crypto.createHash、Module._load、JSON.parse、ipcMain）。
  • 最终版 全部移除，仅保留必要拦截，降低复杂度和潜在冲突。

五、最终版本特性与优缺点

5.1 特性

  • 完整性校验绕过：拦截 fs 模块对 launch.dist.js 的读取，强制返回备份内容。
  • 多层 RSA 解密：
    1. 检测 fn_0212 特殊密文，直接返回预期哈希。
    2. 尝试用攻击者公钥解密。
    3. 回退到伪造的 LICENSE_DATA（填充 256 字节）。
  • 二次校验绕过：拦截 Buffer.prototype.equals，对预期哈希返回 true。
  • 自动设备指纹：从主机名、用户名、Windows GUID 生成 deviceId 和 fingerprint。
  • 注册表自动写入：启动时写入 SLicense 和 IDate。
  • 精准网络拦截：使用 protocol.handle 拦截激活/更新请求，返回伪造成功响应。
  • JSC 字节码加载器：支持 .jsc 和 .cjsc 扩展，确保主程序正常加载。
  • 环境变量支持：通过 TYPORA_EMAIL 和 TYPORA_LICENSE 自定义凭证。
  • 静默错误处理：所有 Hook 包裹在 try-catch 中，确保不干扰主程序。

5.2 优点

  • 功能完备：涵盖已知所有 Typora 验证点，无需额外工具。
  • 兼容性好：基于标准 Node/Electron API，适配多数版本。
  • 副作用极小：网络拦截精准，不影响正常使用。
  • 代码简洁：无冗余，注释清晰，易于维护。
  • 开箱即用：替换文件后无需任何配置即可生效。

5.3 缺点

  • 依赖备份文件：必须预先将原 launch.dist.js 复制为 launch.dist.bak.js（操作说明已注释）。
  • 攻击者公钥有效性：硬编码的公钥可能随 Typora 更新失效，但 fallback 机制保证仍可工作。
  • 仅适用于 Windows：注册表操作和 GUID 获取依赖 Windows 平台（但 Typora 主要用户为 Windows）。

/**
 * 私钥加密 -> Base64 密文
 */
function typoraEncrypt(plaintext, privateKeyPem) {
  const buf = Buffer.isBuffer(plaintext)
    ? plaintext
    : Buffer.from(String(plaintext), "utf8");
  if (buf.length > 245) {
    throw new Error(`明文过长：${buf.length} > 245 字节（RSA-2048 PKCS1 限制）`);
  }
  const cipher = crypto.privateEncrypt(
    {
      key: privateKeyPem,
      padding: crypto.constants.RSA_PKCS1_PADDING,
    },
    buf
  );
  return cipher.toString("base64");
}

/**
 * Base64 密文 -> 公钥解密 -> 明文
 */
function typoraDecrypt(base64Cipher, publicKeyPem) {
  const cipher = Buffer.from(String(base64Cipher), "base64");
  if (cipher.length !== 256) {
    throw new Error(`密文长度 ${cipher.length} != 256（RSA-2048 模长）`);
  }
  const plain = crypto.publicDecrypt(
    {
      key: publicKeyPem,
      padding: crypto.constants.RSA_PKCS1_PADDING,
    },
    cipher
  );
  return plain.toString("utf8");
}
